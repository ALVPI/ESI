	\section{Introducción}
	
	Para esta práctica estaremos empleando un servidor de autenticación \textit{OAuth2}, el cual es el servidor  por excelencia para hacer de mediación en la tarea de distribución de claves de acceso sobre el que realizaremos pruebas de carga con Locust, el cual es un sistema de monitorización que aplica el modelo \textit{pull}, el cual, está apuntando a nuestro \textit{endpoint} y cada 15 segundos (según lo definido en su \textit{.yml}) anota todo lo que está pasando, estos eventos serán visualizados posteriomente  en Grafana.\\
	De tal manera que tenemos 3 objetivos:
	\begin{enumerate}
		\item Instrumentación del backend con métricas Prometheus (haremos incapie en esta tecnología en el punto \ref{PO}).
		\item Despliegue y configuración de Prometheus y Grafana.
		\item Pruebas de carga y estrés con Locust.
	\end{enumerate}
	
	\subsection{Descripción del sistema bajo prueba}
	
	El backend proporcionado es un servidor de autenticación OAuth2 desarrollado en
	Python con Flask y SQLite, que implementa los tres flujos principales definidos
	en el \hyperlink{https://www.rfc-editor.org/rfc/rfc6749.html}{RFC 6749}:
	
	\begin{itemize}
		\item \textbf{Authorization Code}: flujo orientado a aplicaciones web donde
		un usuario humano se autentica mediante un formulario de login. El servidor
		emite un código temporal que posteriormente se canjea por un par de tokens.
		\item \textbf{Client Credentials}: flujo orientado a aplicaciones máquina a
		máquina donde no hay un usuario humano. La aplicación se autentica
		directamente con sus credenciales y obtiene un token de acceso.
		\item \textbf{Refresh Token}: flujo que permite renovar un token de acceso
		caducado sin necesidad de repetir el proceso de autenticación completo.
	\end{itemize}
	
	La aplicación se gestiona con \texttt{uv}, el cual ya empleamos en nuestra primera práctica y como se explicó en su informe es un gestor de paquetes para Python( más moderno que el típico pip).\\
	Aquí uv juega un papel fundamental, puesto que con la instrucción \textit{add} de manera automática instalará las librerías y actualiza el .toml del proyecto para registra la dependencia en el \textit{uv.lock}. \\

\section{Métricas que vamos a emplear en la práctica}
	Para esta sección, emplearemos 2 de los 4 tipos de métricas que nos proporciona la apliación:
	\begin{itemize}
		\item \textbf{Counter}: contador de incremento monotónico, esto quiere decir que sólo va a ir aumentando, lo  usaremos para contar eventos como peticiones recibidas, tokens emitidos o errores producidos.\\Por convención, los counters tienen el sufijo \texttt{\_total}.
		\item \textbf{Gauge}: contador clásico,  lo usaremos para valores que fluctúan como memoria usada o conexiones activas.
	\end{itemize}
	\newpage
	
	\subsection{Definición de las métricas que vamos a recoger}
	
	Hemos creado un fichero \textit{metrics.py} en el que hemos añadido todos los contadores, con dos objetivos, por una parte centralizarlo todo en un fichero, facilitando el desarrollo y la depuración del código y por otra parte, evitar las importaciones circulares de módulos.\\ 
	Este fenómeno ocurre cuando dos ficheros se importan entre ellos, es decir, si por ejemplo en \textit{oauth2\_metrics.py} importamos cosas de \textit{app.py} y en el último importamos fucniones del primero, esto lo solucionamos gestionando todos los contadores en un mismo fichero.\\

	\subsection {Deciciones importantes sobre \textit{metrics.py}}
	
	Una decisión de diseño importante fue no añadir \texttt{client\_id} en etiquetas como  \texttt{tokens\_issued}. Aunque inicialmente se contempló para tener información categorizadas por  clientes, se descartó porque Prometheus crea una serie temporal por cada combinación única de etiquetas. Con una etiqueta de alta cardinalidad como \texttt{client\_id} el número de series crecería proporcionalmente al número de clientes, lo que en una VM con 2GB de RAM podría causar problemas de memoria durante las pruebas de carga.

	\section{Modificaciones a \textit{models.py}}
	\textit{models.py} es la capa de acceso a datos. Se ha instrumentado con métricas en las siguientes funciones:
	
	\subsection{store\_authorization\_code}
	
	Se incrementa \texttt{pending\_auth\_codes} cada vez que se genera un código
	de autorización, reflejando que existe un código emitido pero no canjeado:
	
	\begin{lstlisting}[style=python, caption=Instrumentacion de store\_authorization\_code]
		def store_authorization_code(...) -> str:
		# ... codigo original ...
		db.commit()
		# A new code has been issued but not yet consumed
		pending_auth_codes.inc()
		return code
	\end{lstlisting}
	
	\subsection{consume\_authorization\_code}
	
	Se decrementa \texttt{pending\_auth\_codes} cuando el código se consume
	correctamente. Además se detectan dos casos de seguridad relevantes: el
	intento de reutilización de un código ya usado (\texttt{auth\_code\_reuse})
	y el intento de uso de un código expirado:
	
	\begin{lstlisting}[style=python, caption=Instrumentacion de consume\_authorization\_code]
		def consume_authorization_code(code: str) -> Optional[dict]:
		# ... codigo original ...
		if data["used"]:
		# Someone is trying to reuse an already consumed code
		# This is a sign of an authorization code replay attack
		auth_code_reuse.inc()
		return None
		
		if time.time() > data["expires_at"]:
		return None
		
		db.execute("UPDATE authorization_codes SET used = 1 ...")
		db.commit()
		# Code consumed correctly, no longer pending
		pending_auth_codes.dec()
		return data
	\end{lstlisting}
	
	\subsection{issue\_token\_pair}
	
	Se incrementan los gauges de tokens activos cada vez que se emiten tokens.
	Se distingue entre access tokens y refresh tokens:
	
	\begin{lstlisting}[style=python, caption=Instrumentacion de issue\_token\_pair]
		def issue_token_pair(...) -> dict:
		# ... codigo original ...
		db.commit()
		# Track active tokens in the system
		active_tokens.labels(token_type="access").inc()
		if refresh_token:
		active_tokens.labels(token_type="refresh").inc()
		return response
	\end{lstlisting}
	
	\subsection{validate\_refresh\_token}
	
	Detectamos los dos casos de fallo relevantes para la seguridad: el intento de uso de un token revocado y el de uso de uno expirado.\\ Es importante que estos contadores se incrementen aquí en \texttt{models.py} y no en \texttt{oauth2\_routes.py}, porque esta función tiene acceso directo al motivo exacto del fallo y nos evitamos meter ruido en las métricas:
	
	\begin{lstlisting}[style=python, caption=Instrumentacion de validate\_refresh\_token]
		def validate_refresh_token(token: str) -> Optional[dict]:
		# ... codigo original ...
		if data["revoked"]:
		# Someone is using a token after it has been revoked
		# This is a sign of a token replay attack
		revoked_token_usage.inc()
		return None
		
		if time.time() > data["expires_at"]:
		# Someone is trying to use an expired token
		expired_token_usage.inc()
		return None
		
		return data
	\end{lstlisting}
	
	\subsection{revoke\_refresh\_token}
	
	Incrementamos los \textit{counter}s de \textit{tokens} revocados y se decrementan los \textit{gauges} de \textit{tokens} activos. La rotación de \textit{tokens }del flujo \texttt{refresh\_token} revoca tanto el refresh token antiguo como su access token asociado:
	
	\begin{lstlisting}[style=python, caption=Instrumentacion de revoke\_refresh\_token]
		def revoke_refresh_token(token: str) -> None:
		# ... codigo original ...
		db.commit()
		# Both the refresh token and its associated access token are revoked
		tokens_revoked.labels(token_type="refresh").inc()
		tokens_revoked.labels(token_type="access").inc()
		# Decrement active tokens accordingly
		active_tokens.labels(token_type="refresh").dec()
		active_tokens.labels(token_type="access").dec()
	\end{lstlisting}

	Los \textbf{decoradores} (\texttt{@before\_request} y \texttt{@after\_request}) son \textit{hooks} de Flask que se ejecutan automáticamente antes y después de cada petición HTTP respectivamente, obligando a cada uno de las peticiones a pasar por ellos, haciendo que nuestras métricas recojan los datos, además, nos permite registrar todas las peticiones en un único lugar sin modificar cada ruta individualmente, siguiendo el principio DRY (\textit{Don't Repeat Yourself}).\\

	\section{Modificaciones a\textit{ app.py}}
	
	Se han añadido dos instrumentaciones importantes en \texttt{app.py} mediante decoradores Flask.
	
	\subsection{Exposición del endpoint /metrics}
	
	Se utiliza \texttt{DispatcherMiddleware} para combinar la aplicación Flask
	con la mini aplicación de Prometheus que genera el endpoint \texttt{/metrics}.
	Esto permite que Prometheus pueda leer las métricas en
	\texttt{http://localhost:5001/metrics}:
	
	\begin{lstlisting}[style=python, caption=Exposicion del endpoint /metrics]
		from prometheus_client import make_wsgi_app
		from werkzeug.middleware.dispatcher import DispatcherMiddleware
		from werkzeug.serving import run_simple
		
		if __name__ == "__main__":
		flask_app = create_app()
		# Combine Flask with the Prometheus /metrics endpoint
		application = DispatcherMiddleware(flask_app, {
			"/metrics": make_wsgi_app()
		})
		run_simple("0.0.0.0", 5001, application,
		use_reloader=True, use_debugger=True)
	\end{lstlisting}
	
	\subsection{Registro automático de métricas HTTP}
	
	Hemos usado los decoradores \texttt{@before\_request} y \texttt{@after\_request} de Flask para registrar automáticamente todas las peticiones HTTP sin modificar cada ruta individualmente, para así seguir el patrón DRY (\textit{Don't Repeat Yourself}):
	
	\begin{lstlisting}[style=python, caption=Decoradores before y after request]
		@app.before_request
		def before_request():
		# Store arrival time and increment in-progress counter
		g.start_time = time.time()
		requests_in_progress.labels(endpoint=request.path).inc()
		
		@app.after_request
		def after_request(response):
		endpoint = request.path
		
		# General HTTP counter
		http_requests.labels(
		method=request.method,
		endpoint=endpoint,
		status_code=str(response.status_code)
		).inc()
		
		# Specific counters per endpoint
		if "/token" in endpoint:
		http_requests_token.labels(
		method=request.method,
		status_code=str(response.status_code)
		).inc()
		elif "/authorize" in endpoint:
		http_requests_authorize.labels(
		method=request.method,
		status_code=str(response.status_code)
		).inc()
		elif "/admin" in endpoint:
		http_requests_admin.labels(
		method=request.method,
		status_code=str(response.status_code)
		).inc()
		
		# Decrement in-progress and record duration
		requests_in_progress.labels(endpoint=request.path).dec()
		duration = time.time() - g.start_time
		request_duration.labels(
		endpoint=request.path,
		method=request.method
		).observe(duration)
		
		return response
	\end{lstlisting}
	
	
	\subsection{Instrumentación de flujos OAuth2 — oauth2\_routes.py}
	Hemos tenido que modificar este fichero puesto que nuestras métricas afectan a los 3  flujos de nuestra aplicación, siguiendo siempre la misma lógica   se incrementa \texttt{started} al entrar en la función, \texttt{failed} en cada punto de fallo y \texttt{success} junto con los contadores de tokens al completarse con éxito.\\
	Esto se entiende mejor con un ejemplo:
	\begin{lstlisting}[style=python, caption=Fragmento de \_handle\_client\_credentials()]
		def _handle_client_credentials():
		auth_flows_started.labels(
		grant_type="client_credentials").inc()
		
		client_id, err = _authenticate_client()
		if err:
		auth_flows_failed.labels(
		grant_type="client_credentials").inc()
		return _error_response("invalid_client", err, 401)
		
		client = get_client(client_id)
		if client is None or \
		"client_credentials" not in client["grant_types"]:
		auth_flows_failed.labels(
		grant_type="client_credentials").inc()
		return _error_response("unauthorized_client",
		"Client is not authorized for client_credentials")
		
		scope = request.form.get("scope", "")
		token_response = issue_token_pair(
		client_id=client_id,
		scope=scope,
		user_id=None,
		include_refresh=False,
		)
		
		auth_flows_success.labels(
		grant_type="client_credentials").inc()
		tokens_issued.labels(
		token_type="access",
		grant_type="client_credentials").inc()
		access_tokens_issued.labels(
		grant_type="client_credentials").inc()
		# client_credentials no emite refresh token (RFC 6749)
		
		return jsonify(token_response)
	\end{lstlisting}
	
	De tal manera que  el flujo de trabajo de la aplicación es el siguiente
	 \begin{center}
		\texttt{App OAuth2 (5001)} $\rightarrow$ \texttt{Prometheus (9090)} $\rightarrow$ \texttt{Grafana (3000)}
	\end{center}
	Ahora que ya tenemos los dos primeros pasos configurados,  vamos a preparar el grafana.\\
	Lo primero que hacemos es añadir  Prometheus como fuente de datos en \textit{Connections > Data Sources > Add data source}, se configura la URL \texttt{http://localhost:9090} y se verifica la conexión
	con \textit{Save \& Test}, obteniendo el mensaje:
	
	\begin{center}
		\textit{"Successfully queried the Prometheus API."}

\section{Enfoque EDR del sistema de métricas}

El enunciado de la práctica señala explícitamente que uno de los objetivos
de las pruebas de carga es identificar \textit{``si surgen fallos de seguridad
	fruto del alto nivel de carga''} y que \textit{``se podrán añadir métricas
	adicionales''}. Partiendo de este punto, hemos optado por un enfoque orientado
a la ciberseguridad, intentando emular un  EDR (\textit{Endpoint Detection and
	Response}), que permite detectar comportamientos anómalos en tiempo real
durante las pruebas de carga.

Un sistema EDR monitoriza eventos de seguridad en tiempo real para detectar
patrones de ataque como fuerza bruta, reutilización de tokens o intentos de
acceso con credenciales comprometidas. Prometheus y Grafana permiten replicar
este comportamiento de forma sencilla sobre el servidor OAuth2.
