	\section{Introducción}
	
	Para esta práctica estaremos empleando un servidor de autenticación \textit{OAuth2}, el cual es el servidor  por excelencia para hacer de mediación en la tarea de distribución de claves de acceso sobre el que realizaremos pruebas de carga con Locust, el cual es un sistema de monitorización que aplica el modelo \textit{pull}, el cual, está apuntando a nuestro \textit{endpoint} y cada 15 segundos (según lo definido en su \textit{.yml}) anota todo lo que está pasando, estos eventos serán visualizados posteriomente  en Grafana.\\
	De tal manera que tenemos 3 objetivos:
	\begin{enumerate}
		\item Instrumentación del backend con métricas Prometheus (haremos incapie en esta tecnología en \ref{PO}).
		\item Despliegue y configuración de Prometheus y Grafana.
		\item Pruebas de carga y estrés con Locust.
	\end{enumerate}
	
	\subsection{Descripción del sistema bajo prueba}
	
	El backend proporcionado es un servidor de autenticación OAuth2 desarrollado en
	Python con Flask y SQLite, que implementa los tres flujos principales definidos
	en el \hyperlink{https://www.rfc-editor.org/rfc/rfc6749.html}{RFC 6749}:
	
	\begin{itemize}
		\item \textbf{Authorization Code}: flujo orientado a aplicaciones web donde
		un usuario humano se autentica mediante un formulario de login. El servidor
		emite un código temporal que posteriormente se canjea por un par de tokens.
		\item \textbf{Client Credentials}: flujo orientado a aplicaciones máquina a
		máquina donde no hay un usuario humano. La aplicación se autentica
		directamente con sus credenciales y obtiene un token de acceso.
		\item \textbf{Refresh Token}: flujo que permite renovar un token de acceso
		caducado sin necesidad de repetir el proceso de autenticación completo.
	\end{itemize}
	
	La aplicación se gestiona con \texttt{uv}, el cual ya empleamos en nuestra primera práctica y como se explicó en el informe es un gestor de paquetes para Python más moderno que el típico pip, y se ejecuta en el puerto 5001.

	\section{Prometheus}\label{PO}
	
	Prometheus es una base de datos de series temporales de tipo \textit{pull},
	esto quiere decir que es la propia base de datos quien periódicamente consulta
	a las aplicaciones por sus métricas, de tal manera que las aplicaciones toman un papel pasivo, donde solo se encagan de realizar sus tareas y sólo tiene que exponer un \textit{enpoint} llamado \textit{/metrics} con los datos en el mismo formato que emplea esta tecnología.\\
	Para lograr esto vamos a emplear una librería de Python, \texttt{prometheus\_client} la cual  se encarga de gestionar este endpoint y formatear los datos automáticamente. 
	\begin{lstlisting}[style=bash]
		uv add prometheus-client
	\end{lstlisting}
	Aquí uv juega un papel fundamental, puesto que de \textit{add} de manera automática instala la librería, actualiza el .toml del proeycto y registra la dependencia en el \textit{uv.lock}
	
	\subsubsection{Funciones/Métricas que vamos a emplear en la práctica}
	Emplearemos 2 de las 4 métricas que nos proporciona la apliación, puesto que son las que más se adaptan al planteamiento que tenemos para la práctica:
	\begin{itemize}
		\item \textbf{Counter}: contador de incremento monotónico. Solo puede
		crecer. Se usa para contar eventos como peticiones recibidas, tokens
		emitidos o errores producidos. Por convención, los counters tienen el
		sufijo \texttt{\_total}.
		\item \textbf{Gauge}: contador que puede crecer y decrecer. Se usa para
		valores que fluctúan como memoria usada o conexiones activas.
	\end{itemize}

	Los \textbf{decoradores} \texttt{@before\_request} y \texttt{@after\_request}
	son hooks de Flask que se ejecutan automáticamente antes y después de cada
	petición HTTP respectivamente. Esto permite registrar todas las peticiones
	en un único lugar sin modificar cada ruta individualmente, siguiendo el
	principio DRY (\textit{Don't Repeat Yourself}).
	
	El \texttt{DispatcherMiddleware} combina la aplicación Flask con la mini
	aplicación de Prometheus que genera el endpoint \texttt{/metrics}, de modo
	que todo el tráfico a \texttt{/metrics} lo gestiona Prometheus y el resto
	lo gestiona Flask.
	
	\subsection{Instrumentación de flujos OAuth2 — oauth2\_routes.py}
	
	Se modifica \texttt{oauth2\_routes.py} para incrementar los contadores en
	cada uno de los tres flujos de autenticación. La lógica es la misma para
	los tres: se incrementa \texttt{started} al entrar en la función,
	\texttt{failed} en cada punto de fallo y \texttt{success} junto con los
	contadores de tokens al completarse con éxito.
	
	A continuación se muestra el flujo \texttt{client\_credentials} como ejemplo:
	
	\begin{lstlisting}[style=python, caption=Fragmento de \_handle\_client\_credentials()]
		def _handle_client_credentials():
		auth_flows_started.labels(
		grant_type="client_credentials").inc()
		
		client_id, err = _authenticate_client()
		if err:
		auth_flows_failed.labels(
		grant_type="client_credentials").inc()
		return _error_response("invalid_client", err, 401)
		
		client = get_client(client_id)
		if client is None or \
		"client_credentials" not in client["grant_types"]:
		auth_flows_failed.labels(
		grant_type="client_credentials").inc()
		return _error_response("unauthorized_client",
		"Client is not authorized for client_credentials")
		
		scope = request.form.get("scope", "")
		token_response = issue_token_pair(
		client_id=client_id,
		scope=scope,
		user_id=None,
		include_refresh=False,
		)
		
		auth_flows_success.labels(
		grant_type="client_credentials").inc()
		tokens_issued.labels(
		token_type="access",
		grant_type="client_credentials").inc()
		access_tokens_issued.labels(
		grant_type="client_credentials").inc()
		# client_credentials no emite refresh token (RFC 6749)
		
		return jsonify(token_response)
	\end{lstlisting}
	
	Los flujos \texttt{authorization\_code} y \texttt{refresh\_token} siguen
	la misma lógica pero con más puntos de fallo y emiten además un
	\texttt{refresh\_token}, por lo que incrementan cinco contadores en lugar
	de tres al completarse con éxito.

	\section{Enfoque EDR del sistema de métricas}
	
	\subsection{Motivación}
	
	El enunciado de la práctica señala explícitamente que uno de los objetivos
	de las pruebas de carga es identificar \textit{``si surgen fallos de seguridad
		fruto del alto nivel de carga''} y que \textit{``se podrán añadir métricas
		adicionales''}. Partiendo de este punto, se ha optado por un enfoque orientado
	a la seguridad, inspirado en los sistemas EDR (\textit{Endpoint Detection and
		Response}), que permite detectar comportamientos anómalos en tiempo real
	durante las pruebas de carga.
	
	Un sistema EDR monitoriza eventos de seguridad en tiempo real para detectar
	patrones de ataque como fuerza bruta, reutilización de tokens o intentos de
	acceso con credenciales comprometidas. Prometheus y Grafana permiten replicar
	este comportamiento de forma sencilla sobre el servidor OAuth2.

	\section{Modificaciones a metrics.py}
	
	El fichero \texttt{metrics.py} centraliza la definición de todos los contadores.
	Se han añadido los tres tipos de métricas de Prometheus: \texttt{Counter},
	\texttt{Histogram} y \texttt{Gauge}.
	
	El \texttt{Histogram} requiere la definición explícita de \textit{buckets},
	que son los intervalos de tiempo en los que se agrupan las mediciones. Se han
	elegido buckets optimizados para una aplicación web, incluyendo el valor
	\texttt{0.25} que corresponde al umbral de 250ms mencionado en el enunciado:
	
	\begin{lstlisting}[style=python, caption=Histogram con buckets para web]
		request_duration = Histogram(
		"oauth2_request_duration_seconds",
		"Tiempo de respuesta de cada peticion",
		["endpoint", "method"],
		# 0.25 es el umbral de 250ms que marca el enunciado
		buckets=[0.01, 0.05, 0.1, 0.25, 0.5, 1.0, 2.5, 5.0]
		)
	\end{lstlisting}
	
	Una decisión de diseño importante fue no añadir \texttt{client\_id} como
	etiqueta en \texttt{tokens\_issued}. Aunque inicialmente se contempló para
	tener información por cliente, se descartó porque Prometheus crea una serie
	temporal por cada combinación única de etiquetas. Con una etiqueta de alta
	cardinalidad como \texttt{client\_id} el número de series crecería
	proporcionalmente al número de clientes, lo que en una VM con 2GB de RAM
	podría causar problemas de memoria durante las pruebas de carga.

	\section{Modificaciones a models.py}
	
	\texttt{models.py} es la capa de acceso a datos. Se ha instrumentado con
	métricas en cuatro funciones:
	
	\subsection{store\_authorization\_code}
	
	Se incrementa \texttt{pending\_auth\_codes} cada vez que se genera un código
	de autorización, reflejando que existe un código emitido pero no canjeado:
	
	\begin{lstlisting}[style=python, caption=Instrumentacion de store\_authorization\_code]
		def store_authorization_code(...) -> str:
		# ... codigo original ...
		db.commit()
		# A new code has been issued but not yet consumed
		pending_auth_codes.inc()
		return code
	\end{lstlisting}
	
	\subsection{consume\_authorization\_code}
	
	Se decrementa \texttt{pending\_auth\_codes} cuando el código se consume
	correctamente. Además se detectan dos casos de seguridad relevantes: el
	intento de reutilización de un código ya usado (\texttt{auth\_code\_reuse})
	y el intento de uso de un código expirado:
	
	\begin{lstlisting}[style=python, caption=Instrumentacion de consume\_authorization\_code]
		def consume_authorization_code(code: str) -> Optional[dict]:
		# ... codigo original ...
		if data["used"]:
		# Someone is trying to reuse an already consumed code
		# This is a sign of an authorization code replay attack
		auth_code_reuse.inc()
		return None
		
		if time.time() > data["expires_at"]:
		return None
		
		db.execute("UPDATE authorization_codes SET used = 1 ...")
		db.commit()
		# Code consumed correctly, no longer pending
		pending_auth_codes.dec()
		return data
	\end{lstlisting}
	
	\subsection{issue\_token\_pair}
	
	Se incrementan los gauges de tokens activos cada vez que se emiten tokens.
	Se distingue entre access tokens y refresh tokens:
	
	\begin{lstlisting}[style=python, caption=Instrumentacion de issue\_token\_pair]
		def issue_token_pair(...) -> dict:
		# ... codigo original ...
		db.commit()
		# Track active tokens in the system
		active_tokens.labels(token_type="access").inc()
		if refresh_token:
		active_tokens.labels(token_type="refresh").inc()
		return response
	\end{lstlisting}
	
	\subsection{validate\_refresh\_token}
	
	Se detectan los dos casos de fallo relevantes para la seguridad: el intento
	de uso de un token revocado y el intento de uso de un token expirado. Es
	importante que estos contadores se incrementen aquí en \texttt{models.py}
	y no en \texttt{oauth2\_routes.py}, porque esta función tiene acceso directo
	al motivo exacto del fallo:
	
	\begin{lstlisting}[style=python, caption=Instrumentacion de validate\_refresh\_token]
		def validate_refresh_token(token: str) -> Optional[dict]:
		# ... codigo original ...
		if data["revoked"]:
		# Someone is using a token after it has been revoked
		# This is a sign of a token replay attack
		revoked_token_usage.inc()
		return None
		
		if time.time() > data["expires_at"]:
		# Someone is trying to use an expired token
		expired_token_usage.inc()
		return None
		
		return data
	\end{lstlisting}
	
	\subsection{revoke\_refresh\_token}
	
	Se incrementan los counters de tokens revocados y se decrementan los gauges
	de tokens activos. La rotación de tokens del flujo \texttt{refresh\_token}
	revoca tanto el refresh token antiguo como su access token asociado:
	
	\begin{lstlisting}[style=python, caption=Instrumentacion de revoke\_refresh\_token]
		def revoke_refresh_token(token: str) -> None:
		# ... codigo original ...
		db.commit()
		# Both the refresh token and its associated access token are revoked
		tokens_revoked.labels(token_type="refresh").inc()
		tokens_revoked.labels(token_type="access").inc()
		# Decrement active tokens accordingly
		active_tokens.labels(token_type="refresh").dec()
		active_tokens.labels(token_type="access").dec()
	\end{lstlisting}

	\section{Modificaciones a app.py}
	
	Se han añadido dos instrumentaciones importantes en \texttt{app.py} mediante
	decoradores Flask.
	
	\subsection{Exposición del endpoint /metrics}
	
	Se utiliza \texttt{DispatcherMiddleware} para combinar la aplicación Flask
	con la mini aplicación de Prometheus que genera el endpoint \texttt{/metrics}.
	Esto permite que Prometheus pueda leer las métricas en
	\texttt{http://localhost:5001/metrics}:
	
	\begin{lstlisting}[style=python, caption=Exposicion del endpoint /metrics]
		from prometheus_client import make_wsgi_app
		from werkzeug.middleware.dispatcher import DispatcherMiddleware
		from werkzeug.serving import run_simple
		
		if __name__ == "__main__":
		flask_app = create_app()
		# Combine Flask with the Prometheus /metrics endpoint
		application = DispatcherMiddleware(flask_app, {
			"/metrics": make_wsgi_app()
		})
		run_simple("0.0.0.0", 5001, application,
		use_reloader=True, use_debugger=True)
	\end{lstlisting}
	
	\subsection{Registro automático de métricas HTTP}
	
	Se utilizan los decoradores \texttt{@before\_request} y
	\texttt{@after\_request} de Flask para registrar automáticamente todas las
	peticiones HTTP sin modificar cada ruta individualmente. Esto sigue el
	principio DRY (\textit{Don't Repeat Yourself}):
	
	\begin{lstlisting}[style=python, caption=Decoradores before y after request]
		@app.before_request
		def before_request():
		# Store arrival time and increment in-progress counter
		g.start_time = time.time()
		requests_in_progress.labels(endpoint=request.path).inc()
		
		@app.after_request
		def after_request(response):
		endpoint = request.path
		
		# General HTTP counter
		http_requests.labels(
		method=request.method,
		endpoint=endpoint,
		status_code=str(response.status_code)
		).inc()
		
		# Specific counters per endpoint
		if "/token" in endpoint:
		http_requests_token.labels(
		method=request.method,
		status_code=str(response.status_code)
		).inc()
		elif "/authorize" in endpoint:
		http_requests_authorize.labels(
		method=request.method,
		status_code=str(response.status_code)
		).inc()
		elif "/admin" in endpoint:
		http_requests_admin.labels(
		method=request.method,
		status_code=str(response.status_code)
		).inc()
		
		# Decrement in-progress and record duration
		requests_in_progress.labels(endpoint=request.path).dec()
		duration = time.time() - g.start_time
		request_duration.labels(
		endpoint=request.path,
		method=request.method
		).observe(duration)
		
		return response
	\end{lstlisting}
	
	El decorador \texttt{@before\_request} se ejecuta antes de procesar cada
	petición. Se guarda el instante de llegada en \texttt{g.start\_time} y se
	incrementa el gauge de peticiones en curso.
	
	El decorador \texttt{@after\_request} se ejecuta después de procesar cada
	petición, cuando ya se conoce el código de respuesta. Se incrementan los
	counters HTTP, se decrementa el gauge de peticiones en curso y se registra
	la duración en el Histogram mediante \texttt{observe()}.

	\subsection{Diseño del locustfile}
	
	El fichero \texttt{locustfile.py} define una clase de usuario con cinco tareas
	con pesos distintos. Los pesos se han elegido para simular un escenario
	realista donde el 50\% del tráfico es legítimo y el 50\% son ataques:
	
	\begin{table}[H]
		\centering

			\toprule
			\textbf{Tarea} & \textbf{Tipo} & \textbf{Peso} & \textbf{Probabilidad} \\
			\midrule
			valid\_client\_credentials & Tráfico legítimo M2M    & 4 & 40\% \\
			brute\_force\_api          & Ataque fuerza bruta M2M & 2 & 20\% \\
			brute\_force\_user\_login  & Ataque fuerza bruta web & 2 & 20\% \\
			valid\_user\_login         & Tráfico legítimo web    & 1 & 10\% \\
			replay\_attack             & Ataque token replay     & 1 & 10\% \\
			\bottomrule
		\end{tabular}

	\end{table}
	
	\subsection{Descripción de cada tarea}
	
	\textbf{valid\_client\_credentials} — Simula el tráfico normal de una
	aplicación M2M que pide tokens correctamente. Es la tarea más frecuente
	porque en producción la mayoría del tráfico es legítimo. Dispara las métricas
	de \texttt{auth\_flows\_success} y \texttt{access\_tokens\_issued}.
	
	\textbf{brute\_force\_api} — Simula un atacante que intenta adivinar el
	\texttt{client\_secret} mediante fuerza bruta. Envía credenciales incorrectas
	intencionadamente y espera un 401 como respuesta. Dispara
	\texttt{brute\_force\_attempts} y \texttt{auth\_flows\_failed}.
	
	\textbf{brute\_force\_user\_login} — Simula un atacante que intenta adivinar
	la contraseña de un usuario mediante fuerza bruta a través del formulario de
	login. Dispara \texttt{user\_auth\_failed}. Es importante incluir todos los
	campos del formulario (\texttt{action}, \texttt{response\_type}, \texttt{scope}
	y \texttt{state}) para que la app llegue a comprobar las credenciales.
	
	\textbf{valid\_user\_login} — Simula un usuario legítimo haciendo login
	correctamente. Sin esta tarea las métricas de \texttt{authorization\_code}
	exitoso siempre estarían a cero durante las pruebas, lo que no reflejaría
	la realidad.
	
	\textbf{replay\_attack} — Simula un atacante que intenta reutilizar un token
	de acceso como si fuera un refresh token. Este escenario replica un ataque
	de tipo token replay donde el atacante ha robado un token e intenta usarlo
	fuera de su contexto. Dispara \texttt{revoked\_token\_usage}.
