	\section{Introducción}
	
	En esta práctica estaremos empleando un servidor de autenticación \textit{OAuth2}, el estándar por excelencia para hacer de mediación en la tarea de distribución de claves de acceso.\\
	Sobre él, realizaremos pruebas de carga con Locust y recogeremos los resultados con Prometheus.\\
	De tal manera que tenemos 3 objetivos:
	\begin{enumerate}
		\item Instrumentación del backend con métricas Prometheus (haremos hincapié en esta tecnología en el punto \ref{PO}).
		\item Despliegue y configuración de Prometheus y Grafana.
		\item Pruebas de carga y estrés con Locust.
	\end{enumerate}
	
	\subsection{Descripción del sistema bajo prueba}
	
	El backend proporcionado por el profesor está desarrollado en Python con Flask y SQLite, implementando los tres flujos principales definidos en el \hyperlink{https://www.rfc-editor.org/rfc/rfc6749.html}{RFC 6749}:
	\begin{itemize}
		\item \textbf{Authorization Code}: flujo orientado a aplicaciones web donde un usuario humano se autentica mediante un formulario de login. El servidor emite un código temporal que posteriormente se canjea por un par de tokens.
		\item \textbf{Client Credentials}: flujo orientado a aplicaciones máquina a máquina. La aplicación se autentica directamente con sus credenciales y obtiene un \textit{token} de acceso.
		\item \textbf{Refresh Token}: flujo que permite renovar un \textit{token} de acceso caducado sin necesidad de repetir el proceso de autenticación completo.
	\end{itemize}
	
	La aplicación se gestiona con \texttt{uv}, el cual nosotros ya empleamos en nuestra primera práctica y como se explicó en su  respectivo informe es un gestor de paquetes para Python (más moderno que el típico pip).\\
	Aquí uv juega un papel fundamental, puesto que con el comando  \textit{uv add} instalará de manera automática las librerías y actualiza el .toml del proyecto para registra la dependencia en el \textit{uv.lock}. \\

	\section{Prometheus}\label{PO}

\section{Métricas que vamos a emplear en la práctica}
	Para esta sección, emplearemos 2 de los 4 tipos de métricas que nos proporciona la aplicación:
	\begin{itemize}
		\item \textbf{\textit{Counter}}: contador de incremento monotónico, esto quiere decir que sólo va a ir aumentando, lo  usaremos para contar eventos como peticiones recibidas, tokens emitidos o errores producidos.\\Por convención, los counters tienen el sufijo \texttt{\_total}.
		\item \textbf{\textit{Gauge}}: contador clásico,  lo usaremos para valores que fluctúan como memoria usada o conexiones activas.
	\end{itemize}
	
	\subsection{Definición de las métricas que vamos a recoger}
		Hemos creado un fichero \textit{metrics.py}, detallado en el anexo \ref{anexo:metrics.py} \nameref{anexo:metrics.py}, en el que hemos añadido todos los contadores, con dos objetivos, por una parte centralizarlo todo en un fichero, facilitando el desarrollo y la depuración del código y por otra parte, evitar las importaciones circulares de módulos.\\ 
		Este fenómeno ocurre cuando dos ficheros se importan entre ellos, es decir, si por ejemplo en \textit{oauth2\_metrics.py} importamos cosas de \textit{app.py} y en este último hacemos el \textit{import} de funciones del primero, esto lo solucionamos gestionando todos los contadores en un mismo fichero.
		
	\subsection{Sintaxis de los contadores}
		Antes de mostrar todos nuestro trabajo en \textit{metrics}, vamos a explicar un poco la sintaxis de este fichero, puesto que es una tecnología nueva, que al menos en la carrera no hemos tocado mucho:
		\begin{itemize}
			\item  auth\_flows\_started = Counter( : nombre de variable la cual es un contador, la cual sólo puede incrementarse
			\item \enquote{oauth2\_auth\_flows\_started\_total}: nombre de la métrica para su posterior integración con grafana
			\item "Flujos de autenticacion iniciados":  descripción de la metrica
			\item $["grant\_type"]$: la etiqueta para luego poder filtrarlo en el grafana.
			)
		\end{itemize}
		
		%\vspace{1cm}
		%\lstinputlisting[style=python]{./metrics.py}
		%\vspace{1cm}
		
		Las \textbf{etiquetas} (\textit{labels}) permiten que un mismo \textit{counter} almacene valores independientes para cada combinación de etiquetas. Por ejemplo, \texttt{auth\_flows\_started} con la etiqueta \texttt{grant\_type} almacena
		un contador separado para cada tipo de flujo:
\begin{lstlisting}[style=bash]
	oauth2_auth_flows_started_total{grant_type="client_credentials"} 10.0
	oauth2_auth_flows_started_total{grant_type="authorization_code"} 3.0
	oauth2_auth_flows_started_total{grant_type="refresh_token"} 5.0
\end{lstlisting}
		Esta información nos fue útil en fases tempranas de la práctica ya que con un\textit{ curl } íbamos testeando las métricas para cerciorarnos de que realmente se estaban incrementando cuando deberían.
		\subsection {Decisiones importantes sobre \textit{metrics.py}}
			Una decisión de diseño importante fue no añadir \texttt{client\_id} en etiquetas como  \texttt{tokens\_issued}.\\ Aunque inicialmente se contempló para tener información categorizadas por  clientes, se descartó porque Prometheus crea una serie temporal por cada combinación única de etiquetas. Con una etiqueta de alta cardinalidad como \texttt{client\_id} el número de series crecería proporcionalmente al número de clientes, lo que en una VM con 2GB de RAM podría causar problemas de memoria durante las pruebas de carga.

\section{Modificaciones a \textit{models.py}}
		\textit{models.py} es la capa de acceso a datos. Se ha instrumentado con métricas en las siguientes funciones:
		
		\subsection{store\_authorization\_code}
		
			Se incrementa \texttt{pending\_auth\_codes} cada vez que se genera un código
			de autorización, reflejando que existe un código emitido pero no canjeado:
			
			\begin{lstlisting}[style=python, caption=Instrumentación de store\_authorization\_code]
				def store_authorization_code(...) -> str:
				# ... codigo original ...
				db.commit()
				# A new code has been issued but not yet consumed
				pending_auth_codes.inc()
				return code
			\end{lstlisting}
		
		\subsection{consume\_authorization\_code}
		
			Se decrementa \texttt{pending\_auth\_codes} cuando el código se consume correctamente. Además detectamos dos casos de seguridad relevantes: el intento de reutilización de un código ya usado (\texttt{auth\_code\_reuse}) y el intento de uso de uno ya  expirado:
			
			\begin{lstlisting}[style=python, caption=Instrumentación de consume\_authorization\_code]
				def consume_authorization_code(code: str) -> Optional[dict]:
				# ... codigo original ...
				if data["used"]:
				# Someone is trying to reuse an already consumed code
				# This is a sign of an authorization code replay attack
				auth_code_reuse.inc()
				return None
				
				if time.time() > data["expires_at"]:
				return None
				
				db.execute("UPDATE authorization_codes SET used = 1 ...")
				db.commit()
				# Code consumed correctly, no longer pending
				pending_auth_codes.dec()
				return data
			\end{lstlisting}
			
		\subsection{issue\_token\_pair}
		
			Se incrementan los gauges de tokens activos cada vez que se emiten, distinguiendo entre \textit{access }y \textit{refresh tokens:}
			
			\begin{lstlisting}[style=python, caption=Instrumentación de issue\_token\_pair]
				def issue_token_pair(...) -> dict:
				# ... codigo original ...
				db.commit()
				# Track active tokens in the system
				active_tokens.labels(token_type="access").inc()
				if refresh_token:
				active_tokens.labels(token_type="refresh").inc()
				return response
			\end{lstlisting}
			
		\subsection{validate\_refresh\_token}
		
			Detectamos los dos casos de fallo relevantes para la seguridad: el intento de uso de un \textit{token} revocado y el de uso de uno expirado.\\ Es importante que estos contadores se incrementen aquí en \texttt{models.py} y no en \texttt{oauth2\_routes.py}, porque esta función tiene acceso directo al motivo exacto del fallo y nos evitamos meter ruido en las métricas:
			
			\begin{lstlisting}[style=python, caption=Instrumentación de validate\_refresh\_token]
				def validate_refresh_token(token: str) -> Optional[dict]:
				# ... codigo original ...
				if data["revoked"]:
				# Someone is using a token after it has been revoked
				# This is a sign of a token replay attack
				revoked_token_usage.inc()
				return None
				
				if time.time() > data["expires_at"]:
				# Someone is trying to use an expired token
				expired_token_usage.inc()
				return None
				
				return data
			\end{lstlisting}
		
		\subsection{revoke\_refresh\_token}
		
			Incrementamos los \textit{counter}s de \textit{tokens} revocados y se decrementan los \textit{gauges} de \textit{tokens} activos. La rotación de \textit{tokens }del flujo \texttt{refresh\_token} revoca tanto el \textit{refresh token }antiguo como su \textit{access token} asociado:
			
			\begin{lstlisting}[style=python, caption=Instrumentación de revoke\_refresh\_token]
				def revoke_refresh_token(token: str) -> None:
				# ... codigo original ...
				db.commit()
				# Both the refresh token and its associated access token are revoked
				tokens_revoked.labels(token_type="refresh").inc()
				tokens_revoked.labels(token_type="access").inc()
				# Decrement active tokens accordingly
				active_tokens.labels(token_type="refresh").dec()
				active_tokens.labels(token_type="access").dec()
			\end{lstlisting}

	\section{Modificaciones a\textit{ app.py}}
	
		% LEGACY - Se han añadido dos instrumentaciones importantes en \texttt{app.py} mediante decoradores Flask.\\
	
		Modificamos \texttt{app.py} (código con las modificaciones detallado en el anexo \ref{anexo:app.py} \nameref{anexo:app.py}) para exponer el endpoint \texttt{/metrics} y registrar automáticamente todas las peticiones HTTP mediante decoradores Flask.
		
		Los \textbf{decoradores} aplicados (\texttt{@before\_request} y \texttt{@after\_request}) son \textit{hooks} de Flask que se ejecutan automáticamente antes y después de cada petición HTTP,  obligando a cada uno de las peticiones a pasar por ellos.\\
		Esto es lo que permite que nuestras métricas recojan los datos y todas las peticiones en un único lugar sin modificar cada ruta individualmente, siguiendo el principio DRY (\textit{Don't Repeat Yourself}).\\
		Además el \texttt{DispatcherMiddleware} combina la aplicación Flask con la mini aplicación de Prometheus que genera el endpoint \texttt{/metrics}, de modo que todo el tráfico a \texttt{/metrics} lo gestiona Prometheus y el resto lo gestiona Flask.
		
		\subsection{Exposición del endpoint /metrics}
		
			Se utiliza \texttt{DispatcherMiddleware} para combinar la aplicación Flask con Prometheus que genera el endpoint \texttt{/metrics}. Esto permite que pueda leer las métricas en
			\texttt{http://localhost:5001/metrics}:
			
			\begin{lstlisting}[style=python, caption=Exposición del endpoint /metrics]
				from prometheus_client import make_wsgi_app
				from werkzeug.middleware.dispatcher import DispatcherMiddleware
				from werkzeug.serving import run_simple
				
				if __name__ == "__main__":
				flask_app = create_app()
				# Combine Flask with the Prometheus /metrics endpoint
				application = DispatcherMiddleware(flask_app, {
					"/metrics": make_wsgi_app()
				})
				run_simple("0.0.0.0", 5001, application,
				use_reloader=True, use_debugger=True)
			\end{lstlisting}
			
		\subsection{Registro automático de métricas HTTP}
		
			Hemos usado los decoradores \texttt{@before\_request} y \texttt{@after\_request} de Flask para registrar automáticamente todas las peticiones HTTP sin modificar cada ruta individualmente, para así seguir el patrón DRY (\textit{Don't Repeat Yourself}):
			
			\begin{lstlisting}[style=python, caption=Decoradores before y after request]
				@app.before_request
				def before_request():
				# Store arrival time and increment in-progress counter
				g.start_time = time.time()
				requests_in_progress.labels(endpoint=request.path).inc()
				
				@app.after_request
				def after_request(response):
				endpoint = request.path
				
				# General HTTP counter
				http_requests.labels(
				method=request.method,
				endpoint=endpoint,
				status_code=str(response.status_code)
				).inc()
				
				# Specific counters per endpoint
				if "/token" in endpoint:
				http_requests_token.labels(
				method=request.method,
				status_code=str(response.status_code)
				).inc()
				elif "/authorize" in endpoint:
				http_requests_authorize.labels(
				method=request.method,
				status_code=str(response.status_code)
				).inc()
				elif "/admin" in endpoint:
				http_requests_admin.labels(
				method=request.method,
				status_code=str(response.status_code)
				).inc()
				
				# Decrement in-progress and record duration
				requests_in_progress.labels(endpoint=request.path).dec()
				duration = time.time() - g.start_time
				request_duration.labels(
				endpoint=request.path,
				method=request.method
				).observe(duration)
				
				return response
			\end{lstlisting}
		
		
		\subsection{Instrumentación de flujos OAuth2 — oauth2\_routes.py}
			Hemos tenido que modificar este fichero puesto que, nuestras métricas afectan a los 3  flujos de nuestra aplicación.\\
			De cara a esta modificación hemos seguido siempre la siguiente lógica: incrementamos \texttt{started} al entrar en la función, \texttt{failed} en cada punto de fallo y \texttt{success} junto con los contadores de tokens al completarse con éxito.\\
			Esto se entiende mejor con un ejemplo:
			\begin{lstlisting}[style=python, caption=Fragmento de \_handle\_client\_credentials()]
				def _handle_client_credentials():
				auth_flows_started.labels(
				grant_type="client_credentials").inc()
				
				client_id, err = _authenticate_client()
				if err:
				auth_flows_failed.labels(
				grant_type="client_credentials").inc()
				return _error_response("invalid_client", err, 401)
				
				client = get_client(client_id)
				if client is None or \
				"client_credentials" not in client["grant_types"]:
				auth_flows_failed.labels(
				grant_type="client_credentials").inc()
				return _error_response("unauthorized_client",
				"Client is not authorized for client_credentials")
				
				scope = request.form.get("scope", "")
				token_response = issue_token_pair(
				client_id=client_id,
				scope=scope,
				user_id=None,
				include_refresh=False,
				)
				
				auth_flows_success.labels(
				grant_type="client_credentials").inc()
				tokens_issued.labels(
				token_type="access",
				grant_type="client_credentials").inc()
				access_tokens_issued.labels(
				grant_type="client_credentials").inc()
				# client_credentials no emite refresh token (RFC 6749)
				
				return jsonify(token_response)

			Al querer hacer un diseño realista del trafico que soportaría un sistema como el nuestro hemos decidido emplear esta distribución teniendo en cuenta que cada usuario espera entre 1 y 3 segundos entre tareas mediante \texttt{wait\_time = between(1, 3)}, para tener en cuenta ese "tiempo de pensar" que tienen los usuarios.\\
			De tal manera que todo el tráfico de nuestra aplicación se divide en estas 3 categorías:
			\begin{itemize}
				\item \textbf{Tráfico legítimo}: 11/22 tareas = 50\%
				\item \textbf{Ataques}: 9/22 tareas = 41\%
				\item \textbf{Monitorización}: 1/22 tareas = 5\%
			\end{itemize}
			Siendo las tareas de administración las que menos peso tienen debido a que en un escenario real, un administrador de una web no se autentica varias veces ni hace un uso similar al de un usuario.
			
			\subsubsection{Tareas de tráfico legítimo}
				\begin{itemize}
						\item \textbf{\texttt{valid\_client\_credentials} (peso 6)} es la tarea más frecuente porque el tráfico M2M es el mayoritario y el  flujo más sencillo, puesto que el servidor solo se encarga de enviar las credenciales correctas al endpoint \texttt{/token}, verificando que la respuesta es un código 200.
						\item \textbf{\texttt{valid\_authorization\_code\_flow} (peso 3)} implementa el flujo completo de autorización en dos pasos: primero realiza el login en \texttt{/authorize} obteniendo un código de autorización de la cabecera \texttt{Location} de la redirección 302, y después canjea ese código en \texttt{/token} por un par de tokens. Ojo esto es clave, ya que sin ella \texttt{pending\_auth\_codes} crecería indefinidamente al emitirse códigos que nunca se consumen.
						\item \textbf{\texttt{valid\_refresh\_token\_flow} (peso 2)} obtiene primero un par de tokens mediante el flujo \texttt{authorization\_code} y después los renueva usando el refresh \textit{token}. Sin esta tarea las métricas \texttt{tokens\_revoked} y \texttt{refresh\_tokens\_issued} siempre serían cero durante las pruebas de carga, ya que la rotación de tokens solo ocurre en este flujo.
						\item \textbf{\texttt{list\_admin\_clients} (peso 1)} consulta el endpoint de administración \texttt{/admin/clients} para generar tráfico en \texttt{http\_requests\_admin}, reflejando el bajo uso previsto del admin.
				\end{itemize}
		
			\subsubsection{Tareas de ataque}
				\begin{itemize}
						\item \textbf{\texttt{brute\_force\_api} (peso 2)} simula un ataque de fuerza bruta M2M enviando credenciales incorrectas contra el endpoint \texttt{/token}. Siempre usa el mismo \texttt{client\_id} con \textit{secrets} distintos.
						\item \textbf{\texttt{brute\_force\_user\_login} (peso 2)} simula un ataque de fuerza bruta web enviando contraseñas incorrectas contra \texttt{/authorize}. Siempre usa el mismo username, lo que lo distingue del \textit{credential stuffing} y dispara.
						\item \textbf{\texttt{auth\_code\_replay\_attack} (peso 1)} canjea el mismo código de autorización dos veces. La primera petición tiene éxito (200) y la segunda falla( 400) porque el código ya está marcado como usado en la base de datos, disparando la métrica \texttt{auth\_code\_reuse}.
						\item \textbf{\texttt{revoked\_token\_replay\_attack} (peso 1)} simula un ataque de \textit{token replay} en tres pasos: primero obtiene tokens válidos, los rota mediante el flujo \texttt{refresh\_token} revocando el original, e intenta usar el\textit{ token} ya revocado. Dispara \texttt{revoked\_token\_usage}, señal de posible robo de tokens.
						\item 	\textbf{\texttt{invalid\_refresh\_token} (peso 1)} envía un\textit{ refresh token} completamente falso al servidor para ejercitar el camino de error de tokens inválidos y verificar que el servidor responde correctamente con un 400.
				\end{itemize}
			
			\subsubsection{Tareas de ataque EDR}
			Estas tres tareas las hemos añadido específicamente para el enfoque EDR y detectar patrones de ataque:
				\begin{itemize}
						\item \textbf{\texttt{client\_enumeration\_attack} (peso 1)} prueba \texttt{client\_id} comunes como \texttt{admin}, \texttt{root} o \texttt{test} seleccionados aleatoriamente de una lista de diez valores. Simula a un atacante escaneando qué clientes OAuth2 están registrados en el servidor, disparando la métrica	\texttt{unknown\_client\_attempts}.
						\item \textbf{\texttt{credential\_stuffing\_attack} (peso 1)} selecciona aleatoriamente entre ocho pares de credenciales filtradas de otras plataformas y las prueba contra el endpoint \texttt{/authorize}. A diferencia de la fuerza bruta, cada intento usa un username distinto, lo que hace subir el \textit{gauge} \texttt{unique\_failed\_usernames\_active} y permite distinguir los dos tipos de ataque en el dashboard EDR.
						\item \textbf{\texttt{token\_harvesting\_attack} (peso 1)} solicita tokens válidos sin revocarlos ni renovarlos nunca. Hace que \texttt{active\_tokens} suba sin que \texttt{tokens\_revoked} lo acompañe proporcionalmente.
				\end{itemize}
				
	
		
		\subsection{Decisiones de diseño relevantes}
		
			\begin{itemize}
				\item \textbf{\texttt{catch\_response=True}} se usa en todas las tareas de ataque para indicar a Locust que una respuesta 401 o 400 es el comportamiento esperado y no debe contabilizarse como fallo en las estadísticas de rendimiento. Sin esto Locust
				marcaría todos los ataques como errores y distorsionaría las métricas de la prueba.
				\item \textbf{\texttt{allow\_redirects=False}} se usa en las peticiones a \texttt{/authorize} para capturar el código de autorización de la cabecera \texttt{Location} antes de que Locust siga la redirección automáticamente. Sin esto el código se perdería y el flujo \texttt{authorization\_code} no podría completarse.
				\item \textbf{Método auxiliar \texttt{\_get\_authorization\_code()}} encapsula el proceso de login y extracción del código de autorización. Es reutilizado por \texttt{valid\_refresh\_token\_flow}, \texttt{auth\_code\_replay\_attack} y \texttt{revoked\_token\_replay\_attack}, siguiendo el principio DRY y facilitando el mantenimiento del código.
				\item \textbf{Importaciones dentro de las tareas} (\texttt{import random}) se usan en los ataques de enumeración y credential \textit{stuffing }para seleccionar aleatoriamente	entre listas de valores, simulando comportamiento real de atacante y generando variedad en las etiquetas de las métricas de Prometheus.
			\end{itemize}

	\section{Enfoque EDR del sistema de métricas}
	
		El enunciado de la práctica señala explícitamente que uno de los objetivos
		de las pruebas de carga es identificar \textit{``si surgen fallos de seguridad
			fruto del alto nivel de carga''} y que \textit{``se podrán añadir métricas
			adicionales''}. Partiendo de este punto, hemos añadido un enfoque orientado
		a la ciberseguridad intentando emular un  EDR (\textit{Endpoint Detection and
			Response}), permitiendo detectar comportamientos anómalos en tiempo real
		durante las pruebas de carga.
		
		Un sistema EDR monitoriza eventos de seguridad en tiempo real para detectar
		patrones de ataque como fuerza bruta, reutilización de tokens o intentos de
		acceso con credenciales comprometidas. Prometheus y Grafana permiten replicar
		este comportamiento de forma sencilla sobre el servidor OAuth2.

						Nuestro código se está ejecutando sobre el servidor de desarrollo integrado de Flask, y el entorno opera bajo un modelo de procesamiento síncrono. Cuando Locust inyecta un volumen de peticiones superior a la capacidad de despacho del servidor, el sistema operativo se ve obligado a encolar las peticiones entrantes en sus \textit{buffers} de red (cola TCP), por este motivo, hay una discrepancia de tiempo entre lo que nos muestra el locust y lo mostrado en la gráfica, nosotros sólo estamos midiendo el tiempo de procesamiento de la petición mientras que locust nos da una visión más cercana al tiempo de usuario, desde que hace click y la web le devuelve el resultado de su petición.\\

Es decir, el sistema comienza a cronometrar en el milisegundo exacto en el que el servidor web acepta la conexión y entrega la petición al código Python, deteniéndose al emitir la respuesta. El código de la aplicación es inherentemente \enquote{ciego} al tiempo que la petición ha pasado esperando en etapas previas.\\
